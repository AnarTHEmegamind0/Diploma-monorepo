\subsection{Төлөв удирдлагын хэрэгжилт}

Мобайл аппын төлөвийн давхарга нь authentication, audit, profile, settings зэрэг урсгалыг provider-style state layer-ээр төвлөрүүлдэг. \texttt{AppProviders.build()} дотор root түвшний provider-ууд бүртгэгдэж, дэлгэцүүд зөвхөн шаардлагатай төлөвөө сонсдог. Энэ нь дараах гурван техникийн үр ашигтай:

\begin{enumerate}
    \item Authentication төлөв глобал түвшинд хадгалагдаж, токен сэргээх логик олон дэлгэц дээр давтагдахгүй.
    \item Audit урсгал дахь campaign, tradeshop, image list, submit state зэрэг харилцан хамааралтай өгөгдлүүд нэг provider дотор төвлөрдөг.
    \item \texttt{notifyListeners()}-ын хүрээг зөв ашигласнаар бүх дэлгэцийг биш, зөвхөн өөрчлөгдсөн widget subtree-г дахин зурдаг.
\end{enumerate}

\subsection{Dependency injection}

FastAPI-ийн \texttt{Depends(...)} механизм нь authentication болон role-based access control-ийг endpoint бүр дээр давтан код бичихгүйгээр хэрэгжүүлэх боломж олгосон. \texttt{get\_current\_auditor}, \texttt{get\_admin\_auditor} зэрэг dependency функцууд HTTP bearer token-г задлах, JWT payload шалгах, auditor record-г MongoDB-ээс авах, идэвхтэй эсэхийг шалгах дарааллыг төвлөрүүлдэг. Ингэснээр \texttt{/api/mobile/*} болон \texttt{/api/campaigns}, \texttt{/api/auditors} зэрэг route-ууд аюулгүй байдлын ижил логикийг дахин хэрэглэх боломжтой болсон.

Энэ архитектур нь synchronous framework дээр өргөн хэрэглэгддэг ``request object-оос token гараар задлах'' хэв загвараас илүү тогтвортой. Учир нь dependency graph нь endpoint signature дээрээ ил харагддаг бөгөөд unit test хийхэд dependency-г орлуулах боломжтой.

\subsection{ASGI ба Uvicorn-ийн гүйцэтгэлийн логик}

FastAPI нь ASGI интерфэйс дээр ажилладаг тул нэг worker процесс дотор олон request-ийн I/O хүлээлтийг event loop-р зохицуулж чадна. Энэ төслийн хувьд MongoDB query, файл хадгалалт, authentication шалгалт, mobile API-н олон жижиг read operation зэрэг нь I/O-bound шинжтэй. Ийм үед Uvicorn + ASGI стек нь request thread бүрийг тусгаарлан блоклодог уламжлалт WSGI суурьтай synchronous хувилбараас илүү үр ашигтай ажиллана.

Энэ тайлбар нь ``FastAPI нь үргэлж Flask-аас хурдан'' гэсэн хэт ерөнхий дүгнэлт биш юм. Харин тухайн төслийн workload-д ямар ялгаа гарч буйг заана:

\begin{itemize}
    \item MongoDB-ийн \texttt{find\_one}, \texttt{to\_list}, \texttt{insert\_one} үйлдлүүд await-able тул event loop-д ээлжлэн гүйцэтгэгдэнэ.
    \item Олон auditor зэрэг history, campaigns, survey payload дуудах үед waiting time нь worker-г бүрэн эзлэхгүй.
    \item Харин YOLO inference нь compute-bound тул ASGI alone хангалтгүй; энэ талаар дараагийн дэд хэсэгт тайлбарлав.
\end{itemize}

MongoDB нь энэхүү системд detection result, auditors, campaigns, surveys, audit responses зэрэг бүтэц нь харилцан адилгүй коллекцуудыг хадгалдаг. Техникийн хувьд хамгийн чухал нь database access layer нь \texttt{motor.motor\_asyncio.AsyncIOMotorClient} ашиглаж буй явдал юм. Motor client-ийн query объектууд await-able байдаг тул FastAPI-ийн event loop-той шууд нийцэж, \texttt{find\_one}, \texttt{insert\_one}, \texttt{to\_list} зэрэг үйлдлүүд асинхрон урсгалаар гүйцэтгэгдэнэ.

Энэ нь аудит submit хийх гол урсгал дээр онцгой ач холбогдолтой. Учир нь нэг хүсэлт дээр campaign шалгах, tradeshop шалгах, detection хадгалах, audit response хадгалах зэрэг хэд хэдэн database access дараалан явагддаг. Хэрэв synchronous driver ашигласан бол эдгээр алхам бүр worker-г блоклоно. Харин Motor ашигласнаар I/O хүлээлтийн хугацаанд event loop өөр хүсэлтийг боловсруулах боломжтой хэвээр байна.

\subsection{Docker орчны үүрэг}

Docker нь энэ бүлэгт ``яагаад сонгосон'' гэдэг өнцгөөр бус, системийн runtime орчныг тогтвортой байлгах хэрэгсэл гэсэн өнцгөөр тайлбарлагдана. Төслийн \texttt{docker-compose.yml} файлд MongoDB, backend, frontend гэсэн гурван service тодорхойлогдсон. Backend service нь \texttt{./models}, \texttt{./data}, \texttt{./src} volume-уудыг mount хийж байгаа нь model weight болон inference кодыг container rebuild хийхгүйгээр шинэчлэх хөгжүүлэлтийн хэрэгцээнд нийцсэн бүтэц юм.

Үүний зэрэгцээ Docker орчин нь ML inference stack-д түгээмэл тохиолддог ``local Python орчинд ажилласан ч сервер дээр эвдэрдэг'' асуудлыг багасгана. Ялангуяа OpenCV, PyTorch, Ultralytics зэрэг сангууд version-sensitive байдаг тул backend-ийн runtime dependency-г container дотор хязгаарласнаар дахин давтагдах орчин бүрддэг.
