\chapter{Хэрэгжүүлэлт}

Энэхүү бүлэг нь системийн бүрэлдэхүүн хэсгүүдийг зөвхөн ``юу хийсэн'' түвшинд бус, \textit{яагаад ийм хэрэгжилтийн шийдвэр сонгосон} гэдэг өнцгөөс тайлбарлана. Иймд өгөгдөл бүрдүүлэлт, загвар сургалт, серверийн үйлчилгээ, интерфэйсийн хэрэгжилт, Docker орчны тайлбарууд нь зураг эсвэл кодын хэсгийг давтах бус, тухайн хэрэгжилтийн техникийн үндэслэл, хязгаарлалт, бодит хэрэглээнд үзүүлэх нөлөөг тодруулна.

\section{Өгөгдөл бүрдүүлэлт}

Машин сургалтын загвар нь чанартай өгөгдлөөс шууд хамаардаг \cite{data_augmentation}. George болон Floerkemeier нарын GroZi-120 датасет \cite{grozi_dataset} нь жижиглэн худалдааны барааны анхны нээлттэй датасетуудын нэг байсан бөгөөд бид энэхүү судалгааны арга зүйг өөрийн өгөгдөл бүрдүүлэлтэд ашигласан.

\subsection{Өгөгдөл цуглуулах}

Өгөгдөл цуглуулах үе шат нь detector-ийн бодит хэрэглээний чадварыг тодорхойлох тул зургийн олон янз байдлыг зориуд хадгалах байдлаар төлөвлөгдсөн. Өөрөөр хэлбэл, ижил төрлийн жижиглэн худалдааны барааг зөвхөн ``цэвэр'' нөхцөлд бус, өнцөг, гэрэл, нягт өрөлт, хэсэгчилсэн халхлалттай нөхцөлд авч, сургалтын өгөгдөл нь бодит аудитын орчинтой аль болох ойролцоо байхыг зорьсон. Зургуудыг Улаанбаатар хотын 5 өөр дэлгүүрийн ундаа, усны тасгаас iPhone 12 Pro (12MP) болон Samsung Galaxy S21 (64MP) төхөөрөмжөөр авч, 1920x1080 ба түүнээс дээш нягтралтай хадгалсан. Цуглуулалтын үед байгалийн гэрэл, LED гэрэлтүүлэг, холимог гэрлийн нөхцөл, мөн урд, хажуу, дээрээс авсан 30--60 градусын өнцгийг хамруулсан.

\subsection{Шошгололт}

Цуглуулсан зургуудыг \textbf{Roboflow} платформд байршуулж, YOLO-compatible annotation pipeline бүрдүүлэх зорилгоор шошголсон. Энэхүү платформыг сонгосон шалтгаан нь annotation хийх үйл явцыг хурдасгахаас гадна versioning, augmentation, export pipeline-ийг нэг дор төвлөрүүлдэгт оршино. Энэ нь жижиг хэмжээний академик төслүүдэд data engineering-ийн өртгийг бууруулдаг практик давуу талтай.

Roboflow-ийн гол давуу талууд:

\begin{itemize}
    \item Вэб дээр суурилсан annotation интерфейс
    \item Автомат өгөгдөл баяжуулалт (augmentation)
    \item Датасет хувилбарын удирдлага (versioning)
    \item YOLO формат руу шууд экспортлох боломж
    \item Багийн хамтран ажиллах боломж
\end{itemize}

Шошголсон датасетыг YOLOv8 форматаар экспортлон сургалтад ашигласан.

\subsection{Сургалтын код}

\begin{lstlisting}[language=Python, caption={YOLOv8 training code}]
from ultralytics import YOLO

def train_model():
    model = YOLO("yolov8n.pt")
    results = model.train(
        data="models/configs/dataset.yaml",
        epochs=100,
        batch=16,
        imgsz=640,
        patience=20,
        save=True,
        device=0,
        project="runs/train",
        name="product_detector"
    )
    return results

if __name__ == "__main__":
    train_model()
\end{lstlisting}

Энэхүү кодын гол санаа нь \texttt{yolov8n.pt} pre-trained weight-ийг суурь болгон transfer learning хийхэд оршино. Өөрөөр хэлбэл бүх pipeline-ийг шинээр тодорхойлоогүй, харин Ultralytics-ийн тогтворжсон training loop-ийг ашиглан dataset, epoch, batch, image size зэрэг төсөлд хамаарах параметрүүдийг өөрчилсөн. Энэ нь бакалаврын ажлын хүрээнд reproducibility болон engineering simplicity-ийн хооронд зөв тэнцвэр барихад чиглэсэн шийдвэр юм.

\section{Серверийн хөгжүүлэлт}

Backend серверийг Python FastAPI дээр хэрэгжүүлсэн. Сонголтын гол шалтгаан нь API-ийн оролт, гаралтыг Pydantic схемээр хатуу шалгах, асинхрон I/O урсгалыг дэмжих, мөн inference pipeline-ийг REST үйлчилгээ хэлбэрээр цэгцтэй задлах боломжтой байсанд оршино. Энэ нь Flask зэрэг хөнгөн фреймворктой харьцуулахад type-safe request validation болон OpenAPI баримтжуулалтыг бага нэмэлт өртгөөр авах давуу талтай.

\subsection{Илрүүлэлтийн үйлчилгээ}

\begin{lstlisting}[language=Python, caption={ProductDetector class}]
from ultralytics import YOLO
import numpy as np
from typing import Dict

class ProductDetector:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialize()
        return cls._instance

    def _initialize(self):
        self.model = YOLO("models/weights/product_detector/weights/best.pt")
        self.confidence_threshold = 0.25

    def detect(self, image: np.ndarray) -> Dict:
        results = self.model(image, conf=self.confidence_threshold)[0]
        detections = []
        for box in results.boxes:
            detections.append({
                "class_id": int(box.cls),
                "class_name": self.model.names[int(box.cls)],
                "confidence": float(box.conf),
                "bbox": box.xyxy[0].tolist()
            })
        return {"detections": detections, "total": len(detections)}
\end{lstlisting}

\subsubsection{Singleton маягийн хэрэгжилтийн тайлбар}

Дээрх кодын \texttt{\_\_new\_\_()} ба \texttt{\_initialize()} бүтэц нь \texttt{ProductDetector}-ийг нэг удаа үүсгээд дахин ашиглах зорилготой. YOLO model weight-ийг request бүрт дахин унших нь API latency-д мэдэгдэхүйц нөлөөлөх учраас энэ шийдэл нь inference service-ийн хамгийн чухал оптимизаци юм. Практик утгаараа эхний хүсэлт model-ийг санах ойд байршуулж, дараагийн хүсэлтүүд зөвхөн \texttt{detect()} функцийг ажиллуулна.

\subsubsection{Validation ба async өгөгдлийн урсгал}

FastAPI орчинд request body, query parameter, response schema-г Pydantic модель ашиглан шалгах нь API boundary дээрх алдааг эрт барих давуу талтай. Энэ нь ялангуяа мобайл болон веб клиентаас зэрэг ирэх хүсэлтүүдийн үед өгөгдлийн бүтэц зөрөх эрсдэлийг бууруулна. Нөгөө талаас MongoDB-тэй асинхрон харилцах урсгал нь I/O-bound хугацаанд event loop-г сул байлгах тул нэг хэрэглэгчийн хүсэлт database access хүлээж байх хугацаанд бусад хүсэлтийг блоклохгүй.

Ийм зохиомжийн ач холбогдол нь detector өөрөө compute-bound хэвээр байсан ч серверийн нийт latency-г зөвхөн inference шатанд төвлөрүүлж, түүнээс бусад authentication, persistence, metadata lookup зэрэг шатанд шаардлагагүй саатал үүсгэхгүй байхад оршино.

\subsubsection{Зэрэгцээ хүсэлтийн тухай техникийн хэлэлцүүлэг}

FastAPI route-ууд асинхрон боловч YOLO inference өөрөө compute-bound ажилбар юм. Өөрөөр хэлбэл MongoDB query болон файл хадгалалт нь event loop-той сайн нийцдэг бол \texttt{self.model(...)} дуудлага нь CPU/GPU нөөц дээр бодит тооцоолол хийдэг. Одоогийн архитектурт тусгай inference queue, worker pool, эсвэл \texttt{asyncio.to\_thread()} wrapping хийгдээгүй тул өндөр зэрэгцээ ачаалалтай нөхцөлд throughput-ийг голчлон model inference-ийн хугацаа шийднэ.

\section{Интерфэйсийн хэрэгжүүлэлт}

Системийн хэрэглэгчийн интерфейсийг хоёр үндсэн хэсэгт хуваан хэрэгжүүлсэн: мобайл аппликейшн болон вэб админ самбар.

\subsection{Мобайл аппликейшн}

Аудиторуудад зориулсан мобайл аппликейшнийг Flutter framework ашиглан хэрэгжүүлсэн. Аппликейшний төлөв удирдлагыг provider/Riverpod-той нийцэх provider-centric зохиомжоор, сүлжээний харилцааг \texttt{Dio} клиентээр зохион байгуулсан. Ийм шийдэл нь authentication, campaign selection, image capture, audit result, history зэрэг урсгалыг модуль байдлаар салгаж, UI state болон API side-effect-ийг хольж хутгахгүй байхад чиглэсэн.

Flutter-ийн \texttt{async/await} гүйцэтгэл нь зураг илгээх, нэвтрэх, түүх дуудах зэрэг network request-үүдийг UI thread-оос тусгаарлан хариу хүлээх хугацаанд интерфэйсийг царцаахгүй байхад чухал үүрэгтэй. Иймээс мобайл талын ``хурдан'' мэдрэмж нь зөвхөн backend latency-ээс бус, клиент талын non-blocking event handling-ээс мөн хамаарна.

Энд Odoo framework ашигласан давхар архитектур байхгүй. Энэхүү тайланд дурдагдаж буй мобайл клиент нь Flutter дээр, харин удирдлагын веб самбар нь React.js дээр тус тус хэрэгжсэн бие даасан интерфэйсүүд болно. Ийм тодруулга нь өмнөх хувилбаруудад гарч байсан Flutter/Odoo ойлгомжгүй байдлыг арилгана.
